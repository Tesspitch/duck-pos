# โต๊ะและบิลรวม

เพิ่มจากข้อกำหนดร้านแบบ takeaway ตามการอนุมัติของผู้ใช้ วันที่ 6 พฤศจิกายน 2026 โดยคง QR หน้าร้านเดิมไว้

## วิธีใช้

1. เจ้าของร้านเข้าเมนู **โต๊ะและบิล** (`/tables`) เพิ่มชื่อโต๊ะ และดาวน์โหลด QR ไปวางที่โต๊ะ
2. เปิดรอบขาย โต๊ะพร้อมรับลูกค้าทันที ไม่ต้องกดเปิดโต๊ะทีละตัว
3. ลูกค้าสแกน QR แล้วเลือกเมนูได้เลย ระบบสร้างรอบและบิลพร้อมออเดอร์แรกใน transaction เดียว สั่งเพิ่มจากหลายเครื่องรวมบิลเดียวกัน แต่ละครั้งได้คิวครัวและระบุชื่อโต๊ะ พนักงานเพิ่มรายการจากบิลเดียวกันได้ ปุ่มเปิดบิลเองยังใช้ได้หากพนักงานต้องการเปิดบิลล่วงหน้า
4. กด **คิดเงิน / หยุดรับรายการ** เพื่อหยุดเพิ่มและยกเลิกรายการระหว่างตรวจบิล สามารถกลับไปเปิดรับรายการได้
5. รับชำระรวมครั้งเดียว เงินโอนเป็นค่าเริ่มต้น เงินสดรองรับเงินทอน ยอดและราคาใช้ค่าจากเซิร์ฟเวอร์เสมอ
6. จ่ายแล้วและอาหารครบจะปิดโต๊ะอัตโนมัติ หากจ่ายก่อนอาหารครบ โต๊ะจะคืนพร้อมรับลูกค้าเมื่อพนักงานกดเสร็จแล้วให้รายการสุดท้าย โดยไม่ต้องกลับมากดปิดโต๊ะอีก

หยุดรับออเดอร์ของร้านชั่วคราวได้ระหว่างเคลียร์โต๊ะ แต่จะปิดรอบขายไม่ได้จนปิดโต๊ะและเคลียร์ออเดอร์ค้างครบ โต๊ะที่ยังไม่มีรายการสามารถปิดได้โดยไม่รับชำระ

## การจำรอบและความเป็นส่วนตัว

- QR บนโต๊ะเป็นลิงก์คงที่ `/table/:qrToken` แต่แต่ละรอบเปิดโต๊ะมีบิลคนละ ID
- เบราว์เซอร์เก็บ guest token ต่อบิลใน localStorage เพื่อกลับมาเปิดอีกแท็บหรือปิดแล้วเปิดใหม่ในเบราว์เซอร์และโดเมนเดิม
- ลิงก์ `/table-round/:guestToken` ยึดรอบเดิมตลอด เมื่อจ่ายแล้วแสดงว่าเสร็จสิ้น และไม่เปลี่ยนไปแสดงบิลของลูกค้าชุดถัดไป
- รอบที่ชำระแล้วไม่แสดงปุ่มเริ่มรอบใหม่ ให้สแกน QR โต๊ะอีกครั้งเพื่อเปิดเมนูรอบถัดไปเมื่อโต๊ะพร้อม การเปิดเมนูยังไม่สร้างบิลในฐานข้อมูล
- `ordering_epoch` เปลี่ยนทุกครั้งที่จบรอบโต๊ะ ป้องกันตะกร้าเก่าที่เปิดค้างไว้ถูกส่งเข้ารอบถัดไปโดยไม่ตั้งใจ การส่งซ้ำของคำขอที่เซิร์ฟเวอร์รับไว้แล้วจะยังคืนออเดอร์เดิม
- ลูกค้าเห็นเฉพาะรายการที่ตนสั่ง พนักงานเห็นบิลรวม ยกเลิกเองได้เฉพาะรายการที่ยังรอทำและบิลยังไม่อยู่ระหว่างคิดเงิน
- หากล้างข้อมูลเว็บ เปลี่ยนเบราว์เซอร์ ใช้โหมดส่วนตัว หรือเปลี่ยนโดเมน ข้อมูลที่จำไว้จะไม่ย้ายตาม ควรเก็บลิงก์ติดตามหากต้องเปิดจากอุปกรณ์อื่น

## โครงสร้างและการป้องกัน

- `src/features/dining/domain`: ชนิดข้อมูล สถานะ และข้อความแสดงผล
- `application`: ขอบเขต repository, query/invalidation, การจำรอบและคำขอส่งซ้ำ
- `infrastructure`: Supabase RPC adapter
- `presentation`: หน้าจัดการโต๊ะ บิล เมนูลูกค้า และติดตามรอบ
- Migration `202611060038_dining_tables_and_bills.sql`: โต๊ะ รอบ บิล ใบรับเงิน RLS และ atomic RPC
- Migration `202611060040_automatic_table_rounds.sql`: เปิดรอบอัตโนมัติเมื่อส่งรายการแรก ตรวจ epoch และคืนโต๊ะอัตโนมัติหลังชำระและอาหารครบ
- Migration `202611060041_table_ordering_without_geofence.sql`: ตามการอนุมัติของผู้ใช้ QR โต๊ะไม่ตรวจ GPS หรือรัศมี และไม่ต้องตั้งพิกัดแคชเชียร์ ส่วน QR หน้าร้านยังตรวจรัศมี 100 เมตร
- ไม่มี direct client writes หรือสิทธิ์อ่านบิลสาธารณะ Token เก็บเป็น hash ในฐานข้อมูล
- การคิดเงินล็อกบิลก่อนล็อกออเดอร์ ใช้ fingerprint ตรวจบิลล่าสุด และ idempotency ป้องกันรับชำระซ้ำ
- การเปิดบิลและเปลี่ยนสถานะใช้ lock order ร้าน → โต๊ะ → บิล แล้วจึงออเดอร์ เพื่อรวมคำขอหลายเครื่องและป้องกันบิลซ้อน พร้อม unique constraint สำหรับรอบโต๊ะที่ยังไม่ปิด ไม่ได้ทดสอบการแข่งขันระหว่าง database connections จริงในรอบ QA นี้
- ลงรายการรับเงินใน ledger เดิมของแต่ละออเดอร์ รายงานเดิมจึงรวมยอดครั้งเดียว ใบรับเงินรวมโต๊ะเป็นข้อมูลอ้างอิงเพิ่มเติม
- QR ลูกค้าทั้งสองแบบผ่าน Edge Function เดิมและจำกัดความถี่เหมือนเดิม การสั่งจากโต๊ะตรวจ QR และรอบบิลโดยไม่ขอตำแหน่งอุปกรณ์ การสั่งจาก QR หน้าร้านยังตรวจรัศมี 100 เมตรตามเดิม
- ใช้ `app_private.create_customer_order` เป็นแกนกลางราคา ตัวเลือกสินค้า คิว และ idempotency โดยปิดสิทธิ์เรียกตรงสำหรับทุก client บังคับเส้นทาง QR หน้าร้านให้ตรวจพิกัดเสมอ และยกเว้นได้เฉพาะทางเข้าโต๊ะที่ตรวจความสัมพันธ์ QR/บิลแล้ว
- ไม่ cache บิลหรือสิทธิ์ใน service worker/CDN; localStorage ใช้จำลิงก์เท่านั้น สถานะจริงตรวจจากเซิร์ฟเวอร์
- ดึงเฉพาะหน้าที่เปิด: รายการโต๊ะ 30 วินาที บิล 15 วินาที รอบลูกค้า 7 วินาที/จ่ายแล้ว 15 วินาที หยุดเมื่อซ่อนหน้า และหยุดเมื่อปิดรอบ ไม่มีช่อง Realtime เพิ่ม

## หลักฐานตรวจสอบ

- Lint และ production build ผ่าน; Vitest ผ่าน 40 ไฟล์ 125 ข้อ
- SQL integration: `supabase/tests/0027_dining_tables_flow.test.sql` ผ่าน 46 ข้อบนฐานข้อมูลจริง ทั้งก่อนและหลังใช้ migration โดย rollback fixtures ทั้งหมด
- Regression SQL: 0020 (15), 0022 (36), 0024 (20) ผ่าน ตรวจ QR เดิม การยกเลิก สิทธิ์ และปิดร้าน
- Browser flow: React components จริง + repository จำลองแยกจากยอดขาย บน Chromium 390×844 และ 768×1024: เพิ่มโต๊ะ เปิดโต๊ะ QR preview สั่งสองรอบ ตะกร้า เปิดอีกแท็บ คิดเงิน รับชำระ เปิดรอบใหม่ และลิงก์เก่าหลังจ่าย
- ขนาดหน้าและ dialog ไม่เกิน viewport ตาม `artifacts/qa/dining-responsive-results.json`; ภาพอยู่ใน `artifacts/qa/screenshots/dining-*`
- ยังไม่ได้ทดสอบบนเครื่อง iPhone/iPad จริง และไม่ได้สร้างออเดอร์หรือรับเงินทดสอบในร้านจริง

การเปิดอัตโนมัติ: `verify:production` ผ่าน (lint, Vitest 40 ไฟล์ 132 ข้อ, production build) SQL `0029_automatic_table_rounds.test.sql` ผ่าน 30 ข้อหลังใช้ migration จริง โดย rollback fixtures รวมทั้ง regression 0020 (15), 0024 (20), 0027 (46), 0028 (21) ผ่าน Browser flow ใช้ React components จริงกับ repository จำลองบน Chromium 390×844 และ 768×1024 ตรวจสแกนเข้าเมนูโดยไม่มีบิล สั่งสองรอบ เปิดอีกแท็บ รับชำระ เริ่มรอบใหม่โดยไม่เปิดโต๊ะ และเปิดลิงก์เก่าหลังรอบใหม่สั่งแล้ว ไม่พบหน้า/dialog ล้นจอ หลักฐาน `artifacts/qa/auto-table-responsive.json` และภาพ `artifacts/qa/screenshots/auto-table-*`

## การนำขึ้นใช้งาน

ตรวจเส้นทางโต๊ะ → คิวพนักงานเพิ่มเติม: SQL 0029 ขยายเป็น 40 ข้อและผ่านทั้งหมดบนฐานข้อมูลจริง (rollback fixtures) ยืนยันออเดอร์แรกและรอบสั่งเพิ่มอยู่ใน `list_active_staff_orders` พร้อมชื่อโต๊ะ บิล สถานะ QR และรายการอาหาร ชำระก่อนทำเสร็จยังอยู่ในคิว และหายเมื่อครบทั้งอาหารและเงิน ตรวจ publication จริงพบ `orders` และ `payments` อยู่ใน `supabase_realtime` แล้ว ชุด UI คิว 3 ไฟล์ 9 ข้อผ่าน โดย `TableQueueFlow.test.tsx` ใช้ QueuePage/card/query hooks จริงกับ repository และ callback Realtime จำลอง ตรวจการอัปเดตจากคิวว่างเป็นออเดอร์โต๊ะ การเริ่มทำ เสร็จ และรับชำระ ไม่ได้สร้างออเดอร์ในร้านจริงเพื่อทดสอบ websocket แบบ end-to-end

Migration ถึง 041 และ Edge Function `customer-checkout` อัปเดตบน Supabase แล้ว Frontend ให้ผู้ใช้ deploy build ใหม่บน Cloudflare Pages ตามกระบวนการเดิม QR โต๊ะและ QR หน้าร้านเดิมใช้ต่อได้ ไม่ต้องเปลี่ยนลิงก์

ตรวจยกเว้นตำแหน่ง: SQL 0030 ผ่าน 15 ข้อ และ regression 0029 (40), 0020 (15), 0027 (46) ผ่านหลัง migration โดย rollback ทุก fixture รวม 116 ข้อ ทดสอบตะกร้า 8 ข้อผ่าน รวมกรณีบริการ GPS ปฏิเสธสิทธิ์แต่การสั่งจากโต๊ะยังสำเร็จโดยไม่มีการเรียก capture ตำแหน่ง ส่วน QR หน้าร้านยังเรียก capture และตรวจระยะตามเดิม

ตรวจ CORS ของ Edge Function ด้วย origin `https://duck-pos-ack.pages.dev` ได้ HTTP 204 และ allow-origin ตรงกับโดเมน production
